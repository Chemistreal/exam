# 집필 워크플로 대본

에이전트 여럿에게 집필·검증을 나눠 맡길 때 쓰는 대본이다.

임시 폴더에 두었더니 컨테이너가 재시작될 때마다 사라졌다(세 번). 재료를 만드는
법은 `tools/gen_chunks.py` 로 남겼고, 그 재료를 **어떤 순서로 누구에게 맡기는지**는
여기 남긴다. 둘이 함께 있어야 「같은 방식으로 다시 돌린다」가 사실이 된다.

| 대본 | 하는 일 | 재료 |
|---|---|---|
| `twinbank.js` | 동형문제 집필 → 적대적 반박 → 수리 | `twinsrc/` |
| `perchoice.js` | 선지별 오답 해설 집필 → 반박 → 수리 | `misrc/` |
| `lecmap.js` | 유형 → 개념강의 배선 → 반박 | `lecsrc/` |
| `cropread.js` | 크롭에서 지문·선지 옮김 → 대조 → 수리 | `cropsrc/` |
| `tonefix.js` | 반말·해요체를 평서체로 (뜻은 그대로) | 고칠 파일 목록 |
| `dedupe.js` | 회차를 넘나들며 겹친 동형문제 재집필 | 겹친 쌍 목록 |
| `audit.js` | 「하려다 만 것」 열 각도 훑기 → 세 관점 반박 → 빠진 것 되묻기 | `msg_extract.py` 결과 |
| `thicken.js` | 많이 틀렸는데 얇은 해설 증보 → 반박 → 수리 | `thinsrc/` |
| `thicken-verify.js` | 이미 증보된 원고만 반박 → 수리 (증보 단계 없음) | `thinsrc/` + `answers/_thick/` |

공통 뼈대는 셋이다.

1. **집필** — 원문을 읽고 쓴다.
2. **반박** — 다른 에이전트가 **처음부터 다시 풀어** 틀린 곳을 찾는다.
   통과시키는 것이 아니라 틀린 것을 찾는 것이 목적이라고 못박는다.
3. **수리** — 지적을 **직접 확인한 뒤** 고친다. 반박자가 틀렸으면 고치지 않고 적는다.

3단을 다 거치기 전의 조각은 답지·은행에 넣지 않는다. 실제로 반박 단계가 잡아낸 것들:
지문에 옆 문항의 정답이 새어 있던 자리, 리보솜 하나에 단백질 4.8×10⁵개가 붙는 설정,
「이 실수를 하면 이 값이 나온다」고 적어 놓고 실제로 계산하면 다른 값이 나오는 자리.

## `thicken.js` 가 왜 크롭을 열게 하나

증보 대상 240문항 가운데 **지문이 답지에 글로 있는 것은 열넷뿐**이다. 나머지는
`crops/<시험>/<번호>.png` 에만 있다. 그래서 집필자·반박자 **양쪽 모두**에게
그림을 Read 로 직접 열라고 시킨다. 안 그러면 옛 메모 한 줄을 부풀려 «그럴듯한
틀린 해설» 이 길게 나온다 — 짧은 채로 두는 것보다 나쁘다.

같은 이유로 「크롭이 흐려서 못 읽으면 그 문항은 건드리지 말고 적어라」를 규칙에
넣었다. 채우지 못한 자리는 비어 있는 편이 낫다.

⚠ **정답 키는 이 워크플로가 절대 안 고친다.** 이 회차들은 채점이 끝나 성적이
이미 나갔다. 답이 틀렸다고 판단되면 `reviewNote` 에 적어 선생님께 넘긴다.

## 증보 1차에서 배운 것 (2026-09-02)

아홉 덩어리 90문항을 돌렸더니 **전부에서 결함이 나왔다**(clean 0). 세 단계를
다 거치지 않은 원고를 답지에 넣었더라면 그대로 학생에게 갔다.

반박 단계가 실제로 잡은 것들:

* **jmchc-13 32번** — 반박자가 크롭의 y축 눈금 픽셀 좌표로 선형 보정식을 세워
  네 도표의 값을 다시 읽었다. 집필본의 「첫 봉우리 약 200으로 가장 높다」가
  실제로는 195였고, 가장 높은 것은 다른 도표(≈210)였다.
* **jmchc-14 6번** — 「진한 황산(밀도 약 1.28 g/mL)」. 1.28 은 완충전 납축전지
  **전해액**(37 % 수용액)의 밀도이고 진한 황산은 1.84 다.
* **jmchc-14 2번** — 오답 ①의 함정 설명대로 실수하면 실제로는 ②가 나왔다.
* **donghyung-4 12·24번** — 지문에 없는 원자량을 「주어진 것」으로 적고 있었다.

넷 다 **그림을 안 보고 옛 메모를 부풀린** 자리다. 그래서 2차부터는 두 단계
모두에게 「그림에서 수치를 읽어야 하는 문항이면 눈금과 견주어 값을 직접 재라」
고 명시했고, 「지문에 없는 값을 주어진 것이라고 적지 않는다」를 규칙에 넣었다.

## 「검증만」 대본을 왜 따로 두나

집필은 끝났는데 검증·수리가 중간에 끊기는 일이 실제로 **두 번** 났다(세션 한도).
그때 남는 것은 **아무도 확인하지 않은 원고**다.

처음부터 다시 돌리면 이미 쓴 것을 버리게 되고, 그냥 넣으면 확인 안 한 글이
학생에게 간다. 둘 다 안 된다. 그래서 증보 단계만 떼어 낸 `thicken-verify.js` 를
둔다 — 남아 있는 원고를 그대로 두고 반박부터 시작한다.

반박자에게 **첫 독자가 누구인지 알려 준다**:

> ⚠ 이 증보본은 검증을 못 거친 채 남아 있는 원고다(앞선 실행이 중간에 끊겼다).
>   아무도 아직 이 글을 확인하지 않았다. 네가 첫 독자다.

이 한 줄이 있고 없고가 다르다. 「이미 한 번 걸렀겠지」 하고 훑는 것과
「내가 처음 본다」 하고 읽는 것은 같은 일이 아니다.

## `audit.js` — 「남은 것 없나」를 기억이 아니라 저장소로 답한다

사람이 「이제 남은 건 없지?」라고 물을 때 기억으로 답하면 틀린다. 이 대본은
두 저장소를 **열 각도로 동시에** 훑는다 — 미완 표시자 · 빈 그릇 · 생성기 불일치 ·
CI 구멍 · 문서 대조 · 자산 배선 · 자료 구멍 · 사람 대기 · 요청 대조 · 반쯤 한 것.
각 각도는 서로가 무엇을 찾는지 모른다. 한 각도로는 안 보이는 것이 있기 때문이다.

찾은 것은 **세 관점**이 따로 반박한다 — 「사실인가」·「일부러 그런 것 아닌가」·
「지금 누군가에게 보이는가」. 같은 회의론자 셋보다 서로 다르게 틀릴 수 있는
셋이 낫다. 둘 이상이 통과시켜야 살아남는다.

마지막에 한 명이 **무엇을 못 봤는지** 되묻는다. 열 각도가 구조적으로 놓치는
것, 결과가 한쪽 저장소에만 몰린 것, 두 저장소가 서로 어긋난 자리.

⚠ 「요청 대조」 각도는 `tools/msg_extract.py` 가 뽑은 **사람이 보낸 말**을 읽는다.
  그 파일은 **저장소에 두지 않는다** — 학생 이름이 들어 있다.
